Rendering architecture & pen latency

From pen
to pixels.

Your app remembers a drawing as editable shapes. A renderer turns those shapes into pixels. A GPU API helps execute the work. The operating system and display decide when those pixels become visible.

The important distinction

Skia / Vello, wgpu and Metal are different kinds of tools.

Skia and Vello are alternative renderers. wgpu is an optional portability layer below a renderer. Metal and Direct3D are platform GPU APIs. You do not normally put all of them in one chain.

This is an explanatory guide, not a new benchmark or a platform-support certification. All timing examples below are hypothetical. The production renderer choice remains open.

01 / Who does what?

The document is not the picture of the document.

Imagine drawing one blue stroke. The shared Rust engine stores its real samples and brush settings, supports Undo, and produces its outline. The canvas renderer makes a picture of that state. We can discard and rebuild the picture without losing the editable drawing.

Responsibilities of the layers
LayerPlain-language jobWhat it does not decide
Native interface & inputShows real platform menus and controls; receives pen/mouse events; owns the window and canvas surface.The editable document format or every canvas pixel.
Shared Rust editorKnows what the drawing means: strokes, selection, pressure behavior, editing, history and persistence.Which GPU API must draw it.
Vector renderer: Skia, Vello or customConverts paths, colors, images and clips into pixels; manages coverage, antialiasing and compositing.The physical pen sensor or when the panel emits light.
Optional portability layer: wgpuOffers one GPU interface with several platform backends. It is a Rust library, not a drawing-app engine.How an arbitrary editable stroke should look. We still need a renderer above it.
Platform GPU API: Metal / Direct3D / VulkanCreates GPU resources and submits shader, drawing or compute commands.Undo, brush semantics or a finished vector-rasterization algorithm.
Driver & GPUThe driver connects API commands to the hardware; the GPU executes work and writes images.The entire input-to-visible-pixels delay. CPU work and queues still matter.
Presentation, compositor & displayMakes rendered surfaces available, combines app content where needed, and sends pixels to the display.A guarantee that a submitted frame appeared immediately.

A shader is a small program that runs on the GPU. A texture is image storage the GPU can read or write. A drawable / swap-chain image is an image used for presentation. A compositor combines app surfaces into the desktop or screen. These are implementation tools, not replacements for the editable Rust document.

An API is an interface a program calls; it is not the GPU itself. “DirectX” is Microsoft’s wider technology family. In this discussion, Direct3D is the low-level GPU graphics API, while Direct2D is a higher-level 2D drawing API.

02 / Alternatives, not one long chain

Follow one path at a time.

All these paths can keep native controls and the same Rust document logic. What changes is who turns the shapes into pixels, and how that work reaches the GPU.

Skia’s drawing calls use its own Metal backend, without wgpu in that drawing path. The comparison harness still uses wgpu for shared resource setup and untimed readback.

Possible Windows-specific GPU backend.

Our renderer → Direct3D

  1. Our Rust editorCalled from the native WinUI host
  2. Our custom rendererShared Rust algorithms where practical
  3. Our D3D adapter + shadersWe implement GPU-specific work
  4. Direct3D APIFor example, a D3D12 implementation
  5. Driver + Windows GPUWrites the canvas image

Direct3D handles GPU work. Surface presentation and WinUI composition still require integration.

A different level of abstraction.

Our outlines → native 2D API

  1. Our Rust editorSame document and geometry
  2. Thin platform painterPasses paths, colors and images
  3. Core Graphics OR Direct2DApple and Windows alternatives
  4. Framework rendering internalsBackend and CPU/GPU use are API-dependent
  5. Image → native presentationOS makes the result visible

Core Graphics and Direct2D are alternatives on different platforms. Do not assume Core Graphics is a direct Metal wrapper or that every 2D operation is GPU-executed.

Every GPU path ends with a rendered image that still needs presentation and display. The list is conceptual: calls, resource management and CPU/GPU execution overlap; these boxes are not separate threads or fixed timing costs.

03 / What “direct GPU” really buys

We gain control, and take ownership of more work.

What a custom renderer could exploit

  • Retain committed stroke geometry instead of rebuilding the whole drawing.
  • Update only the active stroke or changed regions.
  • Make pan/zoom a transform change when cached geometry remains suitable.
  • Choose memory use, scheduling and presentation policies around drawing interactions.

What we would need to get right

  • Curves, self-intersections and smooth edge coverage at different zoom levels.
  • Transparency without dark seams where parts of one stroke overlap.
  • Clipping, images, color, resource lifetimes and synchronization.
  • Testing on each target GPU, driver, display and platform surface.

Fewer boxes do not prove less latency. A well-designed library can batch work and reuse caches more effectively than a custom renderer. Conversely, a specialized renderer could do less work for our particular drawing model. That is a hypothesis to test, not a property of the word “direct.”

Some renderer work happens on the CPU. Our tested Vello GPU prepares paths on the CPU before GPU rasterization. Skia also performs CPU-side preparation. Calling either a GPU renderer does not mean the CPU disappears.

My proposed additional candidate is a narrow custom Rust/wgpu renderer, because the product targets multiple platforms. Direct Metal or Direct3D would be justified by concrete platform requirements or measured limitations. This is an experiment proposal, not an implementation or permanent selection.

Metal exposes GPU programming facilities; D3D12’s memory-management guidance illustrates the responsibilities an explicit GPU API puts on the application.

04 / The metric your hand notices

Pen-to-photon latency is the whole journey.

Pen-to-photon latency is the time between a physical pen action and the corresponding visible response from the screen. For moving ink, it is the age of the real pen information represented by the visible stroke.

The renderer controls only part of that journey. A fast render of an old input sample still looks delayed.

Pen is sensed

The digitizer detects position and pressure. Sensor sampling, device processing and transport affect when data becomes available.

OS delivers input

The driver and OS package events. Dispatch, batching and a busy application thread can delay delivery.

App updates the stroke

The host maps input coordinates; Rust applies stroke semantics, pressure/smoothing and produces geometry. Some smoothing deliberately adds lag.

Renderer prepares work

Update paths, caches, buffers and draw commands. Allocations, rebuilding the document or image uploads can stall this stage.

GPU work waits

Already-submitted work, synchronization and contention can keep fresh ink waiting. GPU execution may be fast once it starts.

GPU produces pixels

Rasterize, blend and render the canvas. Complexity, resolution, transparency and memory traffic affect the cost.

Image awaits display

Presentation policy, queued older images, compositor deadlines and refresh timing determine which image is shown next.

Panel emits light

Scanout reaches the relevant screen location and the pixels respond. Panel behavior and screen position affect the physical result.

Conceptual order for tracing one sample, not a promise that every implementation has eight strictly separate stages. CPU work, GPU work and presentation can overlap across frames. Measure timestamps along the sample’s critical path; do not sum overlapping profiling intervals.

Timing terms that should not be confused
TermWhat it meansCommon confusion
Input sample rateHow often the sensor reports positions.A high sample rate does not guarantee immediate delivery or display.
Frame rate / throughputHow many images are produced or displayed per second.A smooth stream can consist of consistently old images.
Display refresh rateHow often the display refreshes; 60 Hz = 16.67 ms, 120 Hz = 8.33 ms, 240 Hz = 4.17 ms per cycle.One refresh period is not the total pen latency, and these rates are not device guarantees.
LatencyDelay for one action or age of input represented by visible ink.It is not simply 1/FPS.
Jitter / tail latencyHow much the delay varies, including occasional slow responses.A good average can hide distracting pauses.

A useful physical intuition: at a constant 500 mm/s, a 20 ms delay corresponds to about 10 mm of travel. That is an illustrative calculation, not a measured pen gap. Prediction, direction changes, coordinate mapping and filtering affect the visible gap.

Illustrative extra queue wait: 16.67 ms

2 older images × (1000 ÷ 120 Hz) = 16.67 ms extra wait.

A zero backlog means zero extra backlog delay in this model, not zero physical latency. Real systems can replace frames, schedule differently or miss deadlines. A swap chain with three buffers does not necessarily contain two old frames waiting to display. Queue depth and buffer capacity are different things.

For drawing, we should preserve real input samples for correct geometry while avoiding a backlog of obsolete pictures. That can mean merging pending visual updates into a frame based on the latest state, without throwing away the real pen history.

Microsoft’s DXGI latency guide explains how rendering schedules and presentation queues affect input age. Its specific UWP/DirectX integration is not a ready-made WinUI implementation for our app.

06 / Accurate history, responsive preview

Coalescing, smoothing and prediction do different jobs.

Coalesced samples

Real intermediate samples delivered together. They improve the recorded stroke’s detail. Recovering history does not make those old samples newer.

Real measured history

Smoothing

Reduces noise and produces cleaner curves. A filter that averages older samples or waits for future ones can lag behind the hand. Its strength is a quality/responsiveness tradeoff.

Can add delay

Prediction

Estimates where the pen will be when the image appears. It can reduce the apparent gap, but can overshoot at a corner or when the pen stops.

Temporary visual estimate

Our contract should persist real samples, never predicted positions as truth. A speculative tail belongs in a temporary preview. Corrections must update the affected real sample when the platform provides them. Prediction improves perceived alignment; it does not remove sensor delay or prove lower physical latency.

Apple documents coalesced touch history and predicted touches. Android documents stylus data, low-latency graphics and motion prediction. Availability and behavior must be checked per target; these are not promises that every host currently implements them.

07 / What matters for Native Sketch

Optimize the full ink path, then measure it.

Latency work across the whole pipeline
PriorityProposed actionWhat to watch
Receive fresh inputTimestamp acquisition and event delivery; preserve coalesced real samples and sample corrections.Busy UI thread, event batching, clock mismatches and device-specific sample behavior.
Keep stroke updates smallUpdate active geometry incrementally; keep disk/network work and document-wide copies out of the ink path.CPU spikes, allocation, locks, heavy smoothing and background tasks.
Separate live ink from stable contentEvaluate a retained base scene with a lightweight transient ink overlay; merge when appropriate.Coverage, opacity and blend correctness at the overlay boundary; stale caches or seams.
Schedule for freshnessAvoid stale visual queues; prepare safe work ahead and use latest input near submission when feasible.Tradeoff between freshness, missed deadlines, GPU utilization and surface availability.
Budget renderer workMeasure path preparation, rasterization, transparency and image upload costs on actual documents.A faster average can hide first-use or p95/p99 stalls.
Treat prediction as a previewUse bounded prediction where supported; replace it cleanly with real data.Overshoot at turns, stopped-pen tails and distracting corrections.
Validate actual devicesTest real pens, displays, power modes and sustained sessions.Refresh rate, resolution, scan position, thermal behavior and OS presentation differences.
Our current renderer comparison did not measure physical pen latency. Its 3.15 ms guarded Skia pan/zoom result is a service-time statistic for a scripted navigation workload, excluding drawable acquisition. It is not “3.15 ms Apple Pencil latency.” Its common GPU timeline also includes CPU/queue gaps; adding the two would double-count work.

Software instrumentation

Track sample IDs and monotonic timestamps from OS events through editor updates, render submission, GPU completion and presentation observations. Verify clock conversions and relate the visible frame to the input it contains. Report missing observations rather than inventing timestamps.

This helps locate delays inside the app, but begins after some physical sensing has happened and does not directly measure panel light.

Physical verification

Use a high-speed camera that captures both the pen action and display response, or a calibrated external rig. Define the event being measured: stroke onset, steady tracking, a sharp turn or pen lift. Repeat across screen positions and workloads.

Record measurement resolution and uncertainty. Report distributions and slow cases, not just the best clip. Test prediction off and on, reporting prediction error separately from timing.

Recommended acceptance work before choosing the final renderer

  1. Agree reference devices, document workloads and acceptable delay/variation targets. We do not yet have a justified universal millisecond target.
  2. Compare the current native painter, Skia, Vello and any custom spike under equivalent live-ink, caching and presentation policies.
  3. Measure stroke onset, continuous motion, turns, pen lift and navigation; include first use, dense scenes, transparency and sustained load.
  4. Combine software traces with physical observation. A screenshot, smooth animation or high FPS alone is insufficient evidence.

The decision is not just “Which library renders fastest?” It is “Which complete input-and-display pipeline keeps correct ink closest to the hand, reliably, on our target devices?”
